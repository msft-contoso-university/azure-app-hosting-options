The abstraction spectrum

Every Azure hosting option trades control against convenience. The further right you move, the more infrastructure you own — and the more operational capability your team needs to sustain it. Start as far left as your requirements allow.

Fully managed apps

You deploy code. Azure owns the OS, runtime, patching, load balancing and scale.

App ServiceStatic Web AppsSpring Apps

Serverless & workflow

You deploy functions or workflows. Azure owns everything else and bills per execution.

FunctionsLogic AppsFoundry Agents

Serverless containers

You deploy container images. Azure owns the cluster, networking fabric and scaling engine.

Container AppsContainer Instances

Managed Kubernetes

You own the cluster configuration, node pools, upgrades and platform add-ons.

AKSRed Hat OpenShift

The default recommendation — if the workload is an HTTP application and you have no hard Kubernetes requirement, start with App Service or Container Apps. Move to AKS or OpenShift only when you need cluster-level extensibility, a specific operator ecosystem, or you already run Kubernetes at scale.

Fully managed applications

Azure App Service

Best for traditional web apps and APIs

A fully managed HTTP platform for web apps, REST APIs and mobile back ends. You deploy code or a container; Azure handles the operating system, runtime patching, load balancing, certificates and scale. It remains the fastest route to production for most line-of-business applications.

Choose it when you have a conventional web application or API, you want zero infrastructure ownership, and you do not need container orchestration primitives. If the app already runs on IIS, Tomcat, Node or .NET, this is usually the lowest-friction destination.

Plans and tiers

Shared & Basic

Free (F1), Basic (B1–B3)

  • Development and proof-of-concept use
  • Manual scale only, no deployment slots
  • No zone redundancy — avoid for production

Standard & Premium

S1–S3, Premium v3 (P0v3–P5v3), Premium v4

  • Autoscale, deployment slots, custom domains
  • Zone redundancy on Premium with two or more instances
  • Premium v3 adds automatic scaling and better price-performance

Isolated v2

App Service Environment v3 (I1v2–I6v2)

  • Single-tenant deployment into your own virtual network
  • Highest scale limits and network isolation
  • For regulated workloads with strict egress control

Managed Instance on App Service — a plan-scoped option for legacy or infrastructure-dependent Windows web apps that need more operating-system customization without giving up managed patching, scaling, diagnostics and identity.

  • Supports PowerShell install scripts for COM components, MSI packages, registry settings, IIS configuration, Windows services, GAC assemblies and selected Windows features.
  • Offers dedicated compute, optional plan-level virtual network integration, Key Vault-backed registry values, Azure Files or UNC mounts, and just-in-time RDP through Azure Bastion for diagnostics.
  • Use it for “lift and improve” migrations that cannot yet move to standard App Service. It is Windows web apps only, available in select regions on Pv4 and Pmv4 plans, and does not support Linux, containers, WebJobs or App Service Environment.

Read the Managed Instance overview on Microsoft Learn →

Resiliency levers

Zone redundancy

On Premium and Isolated v2 plans, instances are spread across physically separate availability zones in the region. A datacentre-level failure removes a fraction of capacity rather than the whole app.

Health check & auto-heal

Configure a health check path and the platform removes failing instances from rotation and replaces them. Auto-heal rules can recycle a worker on memory thresholds, slow requests or specific status codes.

Deployment slots

Deploy to a staging slot, warm it up, then swap. The swap is an instance-level routing change, so rollback is immediate and failed deployments never reach customers cold.

Serverless compute

Azure Functions

Best for event-driven and bursty workloads

Event-driven compute that runs a block of code in response to a trigger — an HTTP request, queue message, blob upload, timer or event stream. The platform owns scaling entirely, and you pay for execution time rather than reserved capacity.

Choose it when work arrives as discrete events, traffic is spiky or unpredictable, and each unit of work completes in a bounded time. Functions is also the cheapest way to run infrequent background processing because idle cost is effectively zero.

Hosting plans

Consumption

  • Scales to zero; billed on GB-seconds and executions
  • Cold starts on first request after idle
  • No virtual network integration

Flex Consumption

  • Scale to zero plus always-ready instances to remove cold start
  • Virtual network integration and zone redundancy
  • Per-instance concurrency control
  • The default choice for new serverless workloads

Premium & Dedicated

  • Premium (EP1–EP3): pre-warmed instances, no cold start, VNet
  • Dedicated: runs on an existing App Service plan
  • Container Apps hosting for container-packaged functions

Resiliency levers

Queue-based buffering

Trigger from Service Bus or Event Hubs rather than direct HTTP where possible. The broker absorbs bursts, preserves messages during downstream outages, and dead-letters poison messages instead of losing them.

Retry policies & idempotency

Trigger bindings support configurable retry with exponential back-off. Because retries mean at-least-once delivery, handlers must be idempotent — key writes on a message identifier.

Durable Functions

For multi-step processes, Durable Functions checkpoints orchestration state. If an instance fails mid-flow, execution resumes from the last checkpoint rather than restarting the whole workflow.

Integration & workflow

Azure Logic Apps

Best for system integration and business process automation

A low-code workflow engine for connecting systems. Rather than writing integration code, you compose a workflow from triggers and actions drawn from over a thousand connectors — SAP, Salesforce, SQL, Dataverse, SharePoint, Service Bus and more — with retry, error handling and run history built into the platform.

Choose it when the problem is moving and transforming data between systems, orchestrating approvals, or implementing B2B exchanges. If most of your code would be API plumbing and retry logic, a workflow engine will be cheaper to build and far cheaper to operate.

Hosting models

Consumption (multi-tenant)

  • Pay per action executed — no idle cost
  • Shared multi-tenant runtime; managed connectors only
  • No virtual network integration
  • Good for low-volume, internet-facing integrations

Standard (single-tenant)

  • Runs on the Azure Functions runtime with WS1–WS3 workload plans
  • Stateful and stateless workflows in the same app
  • Built-in connectors execute in-process — faster and no per-action connector charge
  • Virtual network integration, private endpoints, App Service Environment, and hybrid deployment on Kubernetes

Resiliency levers

Per-action retry policies

Every action has an independent retry policy — fixed interval, exponential back-off or none. Transient downstream failures are absorbed without any custom code or redeployment.

Scopes and run-after

Group actions into scopes and configure run-after conditions to build try / catch / compensate patterns, so a partial failure triggers cleanup rather than leaving the process half-complete.

Checkpointed run history

Stateful workflows persist the output of every action. Runs survive host restarts, and you can inspect or resubmit any historical run — invaluable when reconciling a failed overnight batch.

Globally distributed web front ends

Azure Static Web Apps

Best for modern front ends and content sites

A managed hosting service for static HTML and JavaScript front ends, with globally distributed content, integrated authentication, API back ends and automatic preview environments for pull requests. It is purpose-built for frameworks such as React, Angular, Vue, Svelte, Next.js and Blazor WebAssembly.

Choose it when the browser renders the user experience and the server-side surface is a small API. It removes web-server management entirely while giving development teams a branch-based delivery workflow out of the box.

Plans and delivery model

Free

  • Personal projects, proofs of concept and development
  • Global static content distribution and managed TLS
  • Limited bandwidth, storage and custom-domain capacity

Standard

  • Production SLA, private endpoints and enterprise authentication
  • Managed Functions API or a linked existing API
  • Custom roles, larger quotas and multiple environments

Pull-request environments

  • Every pull request gets an isolated preview URL
  • Front end and API are deployed together from GitHub or Azure DevOps
  • Environment is removed automatically when the branch closes

Resiliency levers

Global edge distribution

Static assets are served from geographically distributed edge locations. Users continue to receive the front end even if one regional point of presence is unavailable.

Decouple the API

Keep the browser shell independently available from the dynamic API. Cache reference data where appropriate and design graceful error states so an API incident does not become a blank page.

Preview before promotion

Branch environments let teams validate routing, authentication and API compatibility against production-like hosting before merging, reducing deployment-caused outages.

Serverless containers

Azure Container Apps

Best for containerised APIs and microservices without cluster operations

A serverless container platform built on Kubernetes, KEDA, Envoy and optional Dapr — without exposing the Kubernetes cluster. You deploy a container image and define ingress, scale rules and revision traffic; Azure operates the control plane, nodes and platform upgrades.

Choose it when applications already ship as containers, need event-driven scale or microservice traffic splitting, but the team does not need Kubernetes APIs, custom operators or control over node pools. It provides most application-platform capabilities with a fraction of AKS operations.

Workload models

Consumption

  • Per-second vCPU and memory billing with a monthly grant
  • Scales from zero to many replicas using HTTP or KEDA rules
  • Ideal for bursty APIs, workers and event processors

Dedicated workload profiles

  • Reserved compute for predictable performance and isolation
  • Multiple profile sizes in one managed environment
  • Supports network-heavy and memory-heavy workloads

Jobs & GPU

  • Manual, scheduled or event-triggered finite jobs
  • Serverless GPU profiles for inference workloads where available
  • Use jobs instead of holding an API replica for background work

Resiliency levers

Zone-redundant environment

Enable zone redundancy when the environment is created, then run at least three replicas for critical services. The platform distributes infrastructure and application replicas across availability zones.

Health probes and KEDA

Startup, readiness and liveness probes keep unhealthy replicas out of rotation. KEDA can scale on queue depth, event lag or a custom metric instead of waiting for CPU pressure.

Immutable revisions

Every application version becomes an immutable revision. Split traffic between old and new revisions for canary validation, then shift or roll back instantly without rebuilding.

Managed Kubernetes

Azure Kubernetes Service

Best for complex platforms that require Kubernetes control

Managed Kubernetes with an Azure-operated control plane and customer-operated node pools. AKS exposes the Kubernetes API and ecosystem: custom resource definitions, operators, service meshes, policy engines, specialised networking and GPU node pools. That flexibility brings the highest operational responsibility in this guide.

Choose it when Kubernetes itself is a requirement: you need custom operators, privileged workloads, specialised networking, a mature internal platform, portability across clusters, or enough services to justify a common orchestration layer. Do not choose it solely because an application is containerised.

Cluster options

Free tier

  • No control-plane charge and no financially backed SLA
  • Development, test and learning clusters
  • You still pay for every node and attached service

Standard tier

  • Production control-plane SLA and higher scale limits
  • 99.95% API-server SLA when availability zones are used
  • Choose Automatic for opinionated defaults or Standard for full configuration

Premium tier

  • Long-term support for selected Kubernetes versions
  • Extended support window for regulated change processes
  • Node VMs, storage, networking and add-ons remain separate costs

Resiliency levers

Zone-aware node pools

Spread system and user node pools across three availability zones, then use topology-spread constraints and pod anti-affinity so replicas do not collapse back onto one node or zone.

Pod disruption budgets

PDBs preserve a minimum number of replicas during voluntary disruptions such as node upgrades. Combine them with readiness probes and surge capacity to upgrade without taking the service offline.

Layered autoscaling

HPA or KEDA scales pods, while Cluster Autoscaler or Node Autoprovisioning adds nodes. Both layers need tested limits; otherwise a constrained node pool can leave newly requested pods pending.

On-demand container compute

Azure Container Instances

Best for isolated tasks and short-lived container groups

The fastest way to run a container in Azure without creating a server or cluster. A container group receives CPU, memory, networking and optional persistent storage, starts in seconds, and is billed per second until it stops. ACI is a compute primitive rather than a complete application platform.

Choose it when one or more tightly coupled containers need to run as a finite task, build agent, data-processing step or emergency burst worker. Use an external orchestrator such as Logic Apps, Functions or Azure Batch when work must be retried, scheduled or scaled.

Execution options

Container groups

  • One or more co-scheduled containers sharing IP, storage and lifecycle
  • Linux and Windows container support
  • Public IP or virtual-network injection

Restart policies

  • Always for service-like processes
  • OnFailure for retriable jobs
  • Never for one-shot tasks whose exit code is inspected externally

Specialised execution

  • Confidential containers protected by AMD SEV-SNP
  • Standby pools reduce startup latency for repeated workloads
  • AKS virtual nodes can burst pods into ACI

Resiliency levers

External orchestration

ACI does not provide application autoscaling, rolling deployments or service-level load balancing. Place a durable orchestrator in front to create, monitor, retry and clean up each container group.

Explicit zone placement

A container group can be pinned to an availability zone, but it does not span zones. For higher availability, launch independent groups in multiple zones and route or partition work externally.

Durable input and output

Keep work items in Service Bus or Queue Storage and write results to durable storage. A failed group can then be replaced without losing its input or relying on ephemeral container files.

Managed Spring application platform

Azure Spring Apps

Best for enterprise Spring Boot portfolios

A managed application platform designed for Spring Boot and Spring Cloud workloads. Azure operates the runtime, service discovery, configuration, routing, certificates, patching and application instances so Java teams can focus on services rather than building a platform around them.

Choose it when an organisation has a meaningful Spring portfolio and wants consistent discovery, configuration, blue-green deployment and observability without operating Kubernetes. Confirm current regional availability, tier options and lifecycle guidance in Microsoft Learn before making a long-term platform decision.

Plans and capabilities

Basic & Standard

  • Managed Spring runtime for development and production workloads
  • Autoscale, service discovery, configuration and diagnostics
  • Standard adds production scale and networking features

Enterprise

  • Commercial VMware Tanzu components and support
  • Application Configuration Service and Service Registry
  • Spring Cloud Gateway, API Portal, Application Live View and Accelerator

Consumption & dedicated

  • Standard consumption and dedicated plan options
  • Linux-based Java and Spring optimisation
  • Enterprise also supports .NET Steeltoe applications

Resiliency levers

Zone redundancy

Where supported, zone-redundant deployment spreads platform infrastructure and application instances across availability zones. Run multiple application instances so a zone loss leaves serving capacity.

Managed discovery and config

Centralised service registration and configuration reduce hard-coded dependencies. Services can discover healthy peers dynamically, while configuration changes are governed independently from application binaries.

Blue-green deployment

Deploy a new version beside the current version, validate it, then switch production traffic. The old deployment remains available for rapid rollback if a regression appears.

Enterprise OpenShift

Azure Red Hat OpenShift

Best for organisations standardised on Red Hat OpenShift

A fully managed OpenShift service jointly engineered and operated by Microsoft and Red Hat. It combines Kubernetes orchestration with the opinionated OpenShift platform: integrated routing, OAuth, operators, an internal registry, developer workflows and Red Hat's enterprise support model.

Choose it when OpenShift is an enterprise standard, workloads depend on certified Red Hat operators or RHEL tooling, or a hybrid estate needs a consistent OpenShift operating model across Azure and on-premises. For a greenfield Azure-only Kubernetes platform, compare the licence and operating model carefully with AKS.

Managed platform scope

Jointly operated service

  • Microsoft and Red Hat operate and support the control plane
  • Three control-plane nodes and a minimum production worker footprint
  • Integrated cluster upgrades and platform lifecycle management

OpenShift application platform

  • HAProxy Router, internal registry and OAuth
  • OperatorHub, Source-to-Image and developer console
  • Pipelines with Tekton and GitOps with Argo CD

Enterprise networking

  • Public or private API and ingress endpoints
  • User-defined routing for controlled egress
  • Integration with Azure private endpoints and network security controls

Resiliency levers

Three-zone topology

Control-plane and worker capacity is distributed across availability zones in supported regions. Applications still need multiple replicas, topology constraints and disruption budgets to benefit from that infrastructure.

MachineSets and autoscaling

MachineSets define repeatable worker pools and the cluster autoscaler adds capacity when pods cannot be scheduled. Separate critical, general and specialised workloads into appropriately sized pools.

GitOps reconciliation

OpenShift GitOps continuously reconciles cluster and application state from source control. Configuration drift is visible and recoverable, while versioned manifests support repeatable regional recovery.

Managed AI agent runtime

Microsoft Foundry Agent Service

Best for governed, observable enterprise AI agents

A managed platform for building, deploying and scaling AI agents. Foundry supports configuration-only prompt agents, managed real-time voice agents, code-based hosted agents, and ephemeral agents that call the Responses API directly. A common runtime brings model access, tools, identity, networking, tracing, evaluation and publishing together.

Choose it when the application needs an agent that reasons across models and tools, maintains conversations, or acts through enterprise systems — and those behaviours require central identity, content safety, tracing, evaluation and lifecycle governance. It is an agent platform, not a replacement for general web hosting.

Decision guide

Start with the workload shape and the operating model the team can sustain. The simplest platform that satisfies the non-negotiable requirements is usually the most resilient choice.

Workload or requirementRecommended starting pointWhy
Traditional .NET, Java, Node or Python web appAzure App ServiceFast migration path, managed runtime, deployment slots, autoscale and strong private-networking options.
Bursty event processing or small HTTP functionsAzure Functions on Flex ConsumptionScale to zero, always-ready capacity, VNet integration and event-native bindings.
SaaS, ERP or B2B system integrationAzure Logic AppsConnector ecosystem, durable run history, retries and low-code exception handling reduce bespoke plumbing.
React, Angular, Vue or static content front endAzure Static Web AppsGlobal edge delivery, managed TLS and authentication, plus automatic pull-request environments.
Containerised API or worker without Kubernetes needsAzure Container AppsServerless scale, revisions, health probes, KEDA and managed ingress without cluster operations.
Custom operators, service mesh, GPU pools or platform APIsAzure Kubernetes ServiceFull Kubernetes extensibility and control, provided a platform engineering team owns the lifecycle.
Short-lived isolated container taskAzure Container InstancesStarts quickly, bills per second and requires no persistent server or cluster.
Large Spring Boot portfolioAzure Spring AppsPurpose-built runtime, discovery, configuration, blue-green deployment and Tanzu capabilities.
Enterprise standard is Red Hat OpenShiftAzure Red Hat OpenShiftJoint Microsoft and Red Hat operations with the full supported OpenShift application platform.
AI agent using models, tools and enterprise dataMicrosoft Foundry Agent ServiceManaged agent runtime, identity, toolboxes, tracing, evaluation, guardrails and publishing lifecycle.

Architecture principle — high availability is not a product checkbox. Pair the selected platform with zone-aware capacity, a resilient data tier, queue-based load levelling where appropriate, tested deployment rollback, end-to-end observability and a rehearsed regional recovery procedure.
